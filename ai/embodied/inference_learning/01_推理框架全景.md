# 01 · 推理框架全景：一次 get_action 的旅程

> 目标：在动手读细节前，先建立一张"地图"，知道一次推理是怎么从传感器观测走到输出动作的。
> 对应代码：`Isaac-GR00T/gr00t/model/policy.py`、`Isaac-GR00T/gr00t/model/gr00t_n1.py`

## 1. 先记住一个核心结论

GR00T N1.5 是一个**双脑（dual-brain）**结构——但它**不是**"显式推理 + 动作"两个独立模型打架，
而是**一个** `GR00T_N1_5` 模型内部由两块分工协作：

1. **Backbone（冻结的 VLM = Eagle 2.5）**：负责"看懂世界"。输入视频帧与语言指令，
   输出 `backbone_features`（视觉-语言特征）。
2. **Action Head（扩散/流匹配 DiT）**：负责"想好动作"。在 `backbone_features` 的条件下，
   从一个**随机噪声**出发，逐步**去噪**，最终还原出一段动作序列 `action_pred`。

推理时**我们不反向传播、不更新权重**，只用 `get_action()` 走一遍前向，把动作算出来。

## 2. 端到端数据流（一张图）

```
               观测 obs (来自机器人/仿真)
   {
     "video.<camera>":  (T,H,W,3) uint8 视频帧
     "state.<joint>":   (T,D)      关节状态
     "annotation.<lang>":(T,)      语言指令
   }
        │  ① Gr00tPolicy.get_action()
        │
        ▼  ② 数据变换 apply_transforms（归一化等）
   normalized_input (已是模型需要的格式/统计意义)
        │  ③ model.get_action()
        │     ├─ backbone(输入)      → backbone_features
        │     └─ action_head 去噪    → action_pred (B, action_horizon, action_dim)
        ▼  ④ 反归一化 unapply_transforms
   unnormalized_action  ← 真实物理意义的动作（作用于机器人）
        │
        ▼  输出动作 dict
   {"action": (T, D)}
```

### 关键点

- **归一化 vs 反归一化**：模型内部工作在一个"标准化"空间（更稳、更好训练）；
  而对外的输入来自真实传感器、输出要作用于真实机器人，所以**入口归一化、出口反归一化**，
  是一对对称操作。这正是第 02 章的专题。
- **`get_action` 是策略统一入口**：无论底层是训练用 `forward` 还是推理用 `get_action`，
  对上层（机器人/服务）都只暴露一个 `get_action`。

## 3. 模块地图：每个模块管什么

| 模块 | 职责 | 一句话原理 | 代码 |
|---|---|---|---|
| `BasePolicy` / `Gr00tPolicy` | 策略封装 | 把"观测 → 动作"做成统一接口 | `policy.py` |
| `GR00T_N1_5` | 模型容器 | 组装 backbone + action_head，定义数据如何进入 | `gr00t_n1.py` |
| `EagleBackbone` | 视觉-语言编码 | 冻结 VLM，把视频/文本变成特征 | `model/backbone/` |
| `FlowmatchingActionHead` | 动作生成 | 流匹配去噪，从噪声还原动作 | `model/action_head/` |
| `ComposedModalityTransform` | 数据变换 | 归一化 / 反归一化 / 增广 | `gr00t/data/transform/` |
| 服务层（后续章节） | 对外接口 | 装成 HTTP/WebSocket / 部署管线 | `inference_service.py` / `vla_infer` |

### 一次 `get_action` 调用的真实代码旅程

在 `policy.py` 中 `Gr00tPolicy.get_action()`：

```python
def get_action(self, observations):
    obs_copy = observations.copy()
    is_batch = self._check_state_is_batched(obs_copy)   # 判断是否批量
    if not is_batch:
        obs_copy = unsqueeze_dict_values(obs_copy)       # 补 batch 维

    # 转成 numpy，保证统一输入类型
    for k, v in obs_copy.items():
        if not isinstance(v, np.ndarray):
            obs_copy[k] = np.array(v)

    normalized_input = self.apply_transforms(obs_copy)          # ① 归一化
    normalized_action = self._get_action_from_normalized_input(normalized_input) # ② 模型前向
    unnormalized_action = self._get_unnormalized_action(normalized_action)      # ③ 反归一化

    if not is_batch:
        unnormalized_action = squeeze_dict_values(unnormalized_action)  # 去掉 batch 维
    return unnormalized_action
```

而在 `_get_action_from_normalized_input` 里，模型在 **inference 且 autocast** 之下运行：

```python
with torch.inference_mode(), torch.autocast(device_type="cuda", dtype=COMPUTE_DTYPE):
    model_pred = self.model.get_action(normalized_input)   # COMPUTE_DTYPE = bfloat16

normalized_action = model_pred["action_pred"].float()      # 转回 float 再反归一化
```

`model.get_action`（在 `gr00t_n1.py`）则是：

```python
def get_action(self, inputs):
    backbone_inputs, action_inputs = self.prepare_input(inputs)  # 拆给 backbone 和 action_head
    backbone_outputs = self.backbone(backbone_inputs)            # 先编码世界
    action_head_outputs = self.action_head.get_action(backbone_outputs, action_inputs) # 再去噪
    self.validate_data(action_head_outputs, backbone_outputs, is_training=False)
    return action_head_outputs
```

## 4. 几个重要概念（先混个眼熟，后续细讲）

- **action_horizon**：一次推理输出的动作**时间步数**；例如一次输出未来 N 帧的动作。
- **action_dim**：动作的**维度**（多少个自由度/关节）。
- **embodiment_tag**：机器人本体的标签（如 GR1、AGIBOT_GENIE1），决定如何解释观测与动作。
  同一个权重可以在不同本体上微调/使用，这就是"具身"泛化的体现。
- **delta_indices / horizon**：观测取哪些时间步（历史帧），动作预测未来哪些步。
- **autocast + bfloat16**：推理用混合精度加速，减少显存，同时保持精度可接受。

## 5. 本章小结

- GR00T 推理 = 一个模型（backbone 看懂 + action head 生成动作）+ 一对"归一化/反归一化"。
- 对外统一入口是 `Gr00tPolicy.get_action()`；对模型统一入口是 `GR00T_N1_5.get_action()`。
- 准备好这些概念后，下一章深入"观测处理与数据变换"。

## 附 · 教学交互中澄清的易混点（FAQ 标注）

> 以下几条来自教学问答中容易混淆的概念，先在此标注，后续章节会用到/展开。

**① “多模态”同名陷阱（第06章会用到）**
- **多模态分布**：`p(action|obs)` 这个分布有多个“峰”（多条互斥但都合理的轨迹）→ 这正是“为什么用去噪生成”的根因。
- **多模态输入**：输入同时来自多种来源（vision 视频/图像 + text 语言 + state 状态）→ 这是 backbone 的一个 feature。
- 两者字面相同、含义不同。GR00T 恰好**两点都有**，所以特别容易弄混：
  - 观测（图像+语言+状态）= 多模态**输入**；
  - 生成动作时面对多个合法解 = 多模态**分布**。
- 注意没有“输入多模态 → 路径多模态”的因果；即便观测是确定的一个，动作仍可能多解。

**② 一次 `get_action` 只产 1 条轨迹：`denoising_steps` ≠ `action_horizon`（第06章展开）**
- `denoising_steps`（缺省约 4）：**1 次** `get_action` 内部，DiT 去噪循环跑 **4 轮**，用来**精修同一条**轨迹。
- `action_horizon`（例如 16）：**这条**轨迹含 **16 个未来时刻**，即 `action_pred` 形状 `(16, action_dim)`。
- 常见误解“一次前向产生 4 个 action_pred” ❌；正确的是 **“4 轮去噪 → 精修出 1 条 (16,D)”**。

**③ 滑动窗口（receding horizon）≠ “把两条轨迹逐点平均”（第08章细节）**
- 每次 `get_action` 都输出一整条未来轨迹；执行时**只取最新预测的靠前几步**，之后用新观测**再滚动预测**。
- 所谓“重叠”指**两次调用在时间轴上的窗口有重合**，**不是**把两次各几条 action_pred 拿来滤波平均。
- 是否对动作再做**平滑/低通**是部署层的**可选工程优化**，并非推理框架的固有机制。

> **类比补充（③'）· 滑动窗口 vs 视频防抖 —— 像 7 分，但有两点要小心**
> - ✅ 共同骨架：两者都是“**一个时间窗口 → 算出‘当前’的输出 → 窗口整体向前滑一步再算**”。
>   视频防抖算第 t 帧用附近若干帧做平滑，下一帧窗口整体前移一格；GR00T 也是“一拍 → 用新观测再预测一条 → 时间轴前移”。
> - ⚠️ 差异 1：防抖窗口是**双向**的（用 t 帧前后取样本），GR00T 推理是**严格因果（单向）**——窗口里绝无未来观测，只用过去观测去预测未来动作。
> - ⚠️ 差异 2：防抖的窗口目的是**估计/平滑**（压抖动的回归/滤波问题）；GR00T 的用途是**用最新观测持续重新生成动作**，两次窗口**不逐点平均**，只用最新预测的前几步。
> - 一句话：这个类比帮你记住“滚动前移”的结构，但要记得 GR00T 是“因果 + 生成 + 不逐点平均”，而不是“双向平滑估计”。

**④ 为什么“从噪声去噪”而不是回归（直击要害版）**
- 根因：条件动作分布**多模态**；回归/取均值会把分布**坍缩成均值**，而均值往往不落在任何一条合法轨迹上（例如“左绕”和“右绕”的平均 = 直直撞上去）。
- 生成式换个思路：**建模条件分布 `p(action|obs)` 并“采样”其中一个模式** → 每次输出都是一条完整、自洽的合法轨迹。
- （flow matching 如何用“速度场”实现“有条件采样”的推导，**保留到第06章细化**。）

## 附 · 课后问答总结（Q&A 交互记录）

> 第一课的问答精华；详细论证见上方「附 · 教学交互中澄清的易混点」的 ①–④/③'。

**Q1 为什么"从噪声去噪"而不是直接回归/一次前向？**
- 根因：条件动作分布**多模态**（同一观测有多条互斥但都合法的轨迹）。回归求**均值**会把分布坍缩成一条
  "不落在任何合法轨迹上"的畸形结果（如"左绕"和"右绕"的平均 = 直直撞上）。
- 生成式 = 建条件分布 `p(action|obs)` 并**采样一个模式** → 每次都是完整、自洽的合法轨迹。
- flow matching 用"速度场"实现这种**有条件采样**的推导，保留到第 06 章。

**Q2 "多模态"到底指哪个？**
- 指**多模态分布**（p(action|obs) 有多个峰），不是**多模态输入**（vision+text+state）。两者同名不同义，
  且无因果：即便观测是一个确定的，动作仍可能多解。（见 FAQ ①）

**Q3 一次 get_action 产出几条轨迹？**
- 1 条。`denoising_steps(=4)` 是"精修同一轨迹跑几轮去噪"，`action_horizon(=16)` 是"这条轨迹多长"。
  "一次产生 4 条"是常见误解。（见 FAQ ②）

**Q4 动作跨窗口靠什么衔接？**
- 滑动窗口（receding horizon）：每次预测一整段未来轨迹、只执行靠前几步、再滚动预测；重叠指时间轴窗口重合，
  **不是**逐点平均两条轨迹。是否做平滑是部署层可选优化，非固有机制。（见 FAQ ③）

**Q5 滑动窗口 ≈ 视频防抖？**
- 只像"结构层"：两者都是"一个时间窗口 → 算当前输出 → 整体前移一步"。但 GR00T 是**因果(单向)+生成+不逐点平均**，
  防抖是**双向+估计/平滑**。类比打 7 分，别把"估计/平滑"误当成 GR00T 的机制。（见 FAQ ③'）
